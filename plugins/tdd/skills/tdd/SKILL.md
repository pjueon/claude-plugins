# TDD 오케스트레이터

이 흐름의 **메인 에이전트가 오케스트레이터**다. 직접 테스트/구현 코드를 짜지 않는다. 워크스페이스를 준비하고, 각 단계를 전용 서브에이전트에 위임하고, 보고를 검증한 뒤 **모든 커밋을 직접** 만든다. 서브에이전트와 같은 워킹트리를 공유하므로, 워커는 디스크만 바꾸고 **커밋하지 않는다.**

구현할 기능: **$ARGUMENTS** (비어 있고 재개할 계획도 없으면 사용자에게 기능을 묻는다.)

| 단계 | subagent_type | model | 역할 |
|------|---------------|-------|------|
| PLAN | `tdd-planner` | opus (에이전트에 고정) | 기능을 사이클로 분해, 사이클별 model 결정, 계획 파일 작성 |
| RED | `tdd-red` | 계획 파일의 `red=` 값 | 실패 테스트 작성 |
| GREEN | `tdd-green` | 계획 파일의 `green=` 값 | 통과시키는 최소 구현 |
| REFACTOR | `tdd-refactor` | 계획 파일의 `refactor=` 값 | `/simplify`로 정리 |
| 문서 | `tdd-docs` | sonnet (에이전트에 고정) | 코드 변경에 맞춰 문서 갱신 |

이 표의 단계가 흐름의 전부다. 계획·검수를 위한 별도 에이전트를 추가로 띄우지 않는다. PLAN이 계획이고, 단계마다 오케스트레이터가 직접 하는 검증이 검수다.

**model 지정**: `model` 파라미터는 에이전트 정의보다 우선하므로 호출 때마다 명시해 넘긴다.
- RED/GREEN/REFACTOR 워커(정의에 model을 고정하지 않음 — `inherit`): 계획 파일의 해당 사이클 `model:` 값을 넘긴다. 값이 없거나 해석할 수 없으면 `sonnet`.
- `tdd-planner`는 `opus`, `tdd-docs`는 `sonnet`을 명시해 넘긴다(정의와 같은 값).

**에스컬레이션**: 단계가 실패하면, 디스크 상태를 그대로 둔 채 직전 시도의 실패 로그를 전달해 **한 단계 위 model**(haiku→sonnet, sonnet→opus)로 **한 번만** 다시 호출한다. 이미 opus였거나 재시도도 실패하면 멈추고 사용자에게 보고한다. "단계 실패"의 정의:
- RED: 올바른 이유로 실패하는 테스트를 만들지 못함.
- GREEN: 전체 스위트를 green으로 만들지 못함, 또는 포맷·검증 게이트에서 실패함.
- REFACTOR: green을 유지하지 못함.
- 워커는 성공을 보고했지만 오케스트레이터가 실제 출력으로 검증해 보니 어긋난 경우도 같다.

서브에이전트는 컨텍스트를 공유하지 않는다. **호출할 때마다 테스트 환경(프레임워크·실행 명령·경로), 사이클 번호/제목/설명, 직전 단계 요약을 명시적으로 전달**한다.

## 계획 파일 (repo 밖, 커밋하지 않음)

진행 상태는 repo가 아니라 사용자 홈 아래에 둔다. 커밋 이력을 어지럽히지 않고, 프로젝트의 폴더 구조와 무관하며, 세션이 끊겨도 남아 재개할 수 있다.

- 상태 폴더: `<홈>/.claude/tdd-state/<repo 루트 폴더명>/`. repo 루트는 `git rev-parse --show-toplevel`. 없으면 만든다. **홈 경로는 시작할 때 한 번 절대 경로로 해석**해 두고(POSIX는 `$HOME`, Git Bash는 `cygpath -m "$HOME"`, PowerShell은 `$HOME`) 이후 도구 호출과 서브에이전트에 그 값을 그대로 쓴다.
- 계획 파일: `<상태 폴더>/tdd/<브랜치명의 /를 -로 바꾼 슬러그>.md`. (`tdd-loop`의 파일은 `<상태 폴더>/loop/` 아래에 있어 섞이지 않는다.)
- 계획 파일의 `저장소:`(repo 루트 절대 경로)와 `브랜치:`가 현재 repo·브랜치와 같은지 확인한다. 다르면(같은 폴더명의 다른 repo, 슬러그가 같아진 다른 브랜치) 멈추고 보고한다.
- 계획 파일을 고치는 것은 오케스트레이터와 planner뿐이고, tdd-docs는 읽기만 한다. 기능이 끝나면 파일을 **삭제**한다(커밋할 것이 없다).

---

## 0. 시작 또는 재개 판정 (한 번만)

현재 브랜치에 해당하는 계획 파일(`tdd/` 폴더, `저장소:`가 현재 repo인 것)이 있는지 확인한다.
- **있으면 → [R] 재개 모드.** (이전 작업이 중단된 것이므로 다시 계획하지 않는다.) 단, 인자로 받은 기능이 계획의 `기능:`과 명백히 다르면 멈추고 한 번만 묻는다(이어서 할지, 새로 시작할지).
- **없으면:**
  - 인자가 비어 있고 이 repo의 미완 계획 파일이 정확히 하나면, 그 계획의 브랜치로 체크아웃해 재개를 제안한다(워킹트리가 깨끗할 때만).
  - 그 외에는 **[1] 신규 모드.** 이 repo의 다른 브랜치용 미완 계획 파일이 있으면 최종 보고에서 알린다.

---

## 1. 신규 모드 — 브랜치 + 계획

1. 워킹트리가 깨끗한지 확인한다(`git status --porcelain`). 변경이 남아 있으면 멈추고 사용자에게 묻는다 (단계별 커밋 규율이 깨끗한 시작에 의존).
2. **브랜치**: 현재가 기본 브랜치(`master`/`main`/`dev`)면 작업 성격에 맞는 prefix로 `<feat|fix|refactor>/<기능-슬러그>`를 만들어 체크아웃한다. 이미 작업 브랜치면 그대로 사용한다. 정한 브랜치명과 시작 커밋 해시(`git rev-parse HEAD`)를 기억한다.
3. **계획**: `tdd-planner`를 띄워 기능 설명, 브랜치명, 시작 커밋 해시, 계획 파일 경로를 전달한다. planner는 기존 테스트를 조사해 프레임워크/컨벤션과 검증 명령을 정하고, 기능을 작은 사이클로 분해하며 사이클별 model을 정해 계획 파일에 저장하고 보고한다.
4. 보고된 계획을 **검토**한다(사이클 크기·순서·완전성, 테스트 환경 타당성, model 선택의 타당성). 필요하면 계획 파일을 직접 고쳐 조정한다.

→ [3] 루프로 들어간다. (계획 파일은 커밋하지 않는다.)

---

## R. 재개 모드

1. 계획 파일을 읽어 기능·브랜치·시작 커밋·테스트 환경·검증 명령·사이클 목록(각 상태 `[ ]`/`[x]`와 model)·발견한 이슈를 복원한다.
2. 현재 브랜치가 계획 파일의 브랜치와 같은지 확인한다(다르면 멈추고 불일치를 보고).
3. **중단 지점 진단**: `git status --porcelain`, `git log --oneline -8`. 반쯤 진행된 사이클이 보이면 어느 단계(RED/GREEN/REFACTOR)부터 이어야 할지 판단한다(깔끔히 판단되지 않으면 멈추고 보고). 깨끗하면 첫 번째 `[ ]` 사이클부터 진행한다.

→ [3] 루프로 들어간다 (재계획하지 않는다).

---

## 3. 사이클 반복

다음 `[ ]` 사이클마다 RED → GREEN → REFACTOR를 순서대로 수행한다. 각 워커에 **테스트 환경 + 사이클 제목·설명 + 직전 단계 요약**을 전달하고, model은 위 규칙대로 넘긴다. 워커가 실패를 보고하면 에스컬레이션 규칙을 적용하고, 그래도 해결되지 않으면 **즉시 멈추고** 사용자에게 보고한다(계획 파일이 남아 재개 가능).

**커밋 메시지**: 프로젝트에 컨벤션이 있으면(기존 `git log`, CONTRIBUTING, CLAUDE.md 등) 그것과 언어를 따른다. 없으면 아래 기본 형식을 쓴다.

- **RED** (`tdd-red`) → 실패 테스트를 보고받는다. 새 테스트가 **올바른 이유로 실패**하는지 실제 출력으로 확인한 뒤, 테스트 파일만 커밋: `test(<슬러그>): <제목> (RED)`. (RED는 실패가 정상이다.)
- **GREEN** (`tdd-green`) → 구현을 보고받는다. **포맷·검증 게이트** 통과 시에만 커밋한다: 계획 파일의 포맷·검증 명령이 있으면 실행하고, 없으면 전체 테스트 스위트를 돌려 **모두 green**을 확인한다. 통과 시 구현 파일만 커밋: `feat(<슬러그>): <제목> (GREEN)`.
- **REFACTOR** (`tdd-refactor`) → 정리 결과를 보고받는다. 변경이 있으면 게이트 통과 후 `refactor(<슬러그>): <제목>` 커밋, 변경이 없으면 GREEN 커밋을 `--amend`해 메시지 끝에 ` (REFACTOR: 변경 없음)`을 덧붙인다 (단계 누락이 아니라 정리할 게 없었음을 히스토리에 남기기 위함).

사이클이 끝나면 계획 파일에서 해당 항목을 `[x]`로 바꾸고 줄 끝에 ` — 커밋: <REFACTOR 또는 amend된 GREEN 해시>`를 기록한다(파일만 고치고 커밋하지 않는다).

남은 `[ ]`가 있으면 묻지 말고 다음 사이클로 자동 진행한다. 모두 `[x]`면 [4]로 간다.

## 4. 마무리 (모든 사이클 완료)

1. **문서** (`tdd-docs`): 한 번 띄운다. 기능 슬러그, 계획 파일 경로, 시작 커밋 해시를 전달한다. 계획 파일과 git log로 작업을 복원해 영향받는 문서를 갱신해 보고한다(커밋하지 않는다). 변경이 있으면 메인이 코드와 분리해 커밋: `docs(<슬러그>): 문서 갱신`. 갱신할 것이 없었다면 커밋하지 않는다.
2. **발견한 이슈 이관**: 계획 파일의 `## 발견한 이슈`를 읽어 둔다. 프로젝트 지침이 버그 기록 방식을 정해 두었고 호출 인자가 "이슈는 보고만"이라고 하지 않았다면 그 방식으로 옮긴다(파일이면 코드와 분리한 별도 커밋). 정해 둔 것이 없으면 이슈를 새로 만들지 않고 보고에만 남긴다.
3. **계획 파일 삭제**: 위 목록을 기억해 둔 뒤 계획 파일을 지운다. 상태 폴더가 비면 폴더도 지운다.
4. 사용자에게 보고: 브랜치명, 사이클 수, 각 사이클 한 줄 요약, skip된 REFACTOR(와 이유), 문서 변경 내역, 발견한 이슈 목록, (있다면) 다른 브랜치의 미완 계획 파일. 브랜치는 체크아웃된 채로 두고, 요청 없이는 merge/push하지 않는다.

## 규칙

- **실패하는 테스트 없이 구현 코드를 쓰지 않는다.** "그냥 코드부터" 하고 싶어지면 그게 RED부터 쓰라는 신호다.
- **한 사이클 = 한 동작.** 한 사이클에 서로 무관한 assertion이 여럿 필요하면 사이클이 너무 큰 것 → 쪼갠다.
- **모든 커밋은 메인이 만든다.** 서브에이전트는 디스크만 바꾸고 보고만 한다.
- **계획 파일은 커밋하지 않는다.** repo 안에 진행 상태 파일을 만들지 않는다.
- **신뢰하지 말고 검증한다.** 단계 사이마다 실제 테스트 출력으로 red/green을 확인한다.
- **무관한 버그 발견 시**: 그 자리에서 고치지 않는다. 계획 파일의 `## 발견한 이슈`에 발견 맥락과 함께 한 줄 추가하고 진행한다. 마무리에서 [4]의 이슈 이관 규칙으로 처리한다.
