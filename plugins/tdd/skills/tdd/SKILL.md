# TDD 오케스트레이터

이 흐름의 **메인 에이전트가 오케스트레이터**다. 직접 테스트/구현 코드를 짜지 않는다. 워크스페이스를 준비하고, 각 단계를 전용 서브에이전트에 위임하고, 보고를 검증한 뒤 **모든 커밋을 직접** 만든다. 서브에이전트와 같은 워킹트리를 공유하므로, 워커는 디스크만 바꾸고 **커밋하지 않는다.**

구현할 기능: **$ARGUMENTS**

| 단계 | subagent_type | 역할 |
|------|---------------|------|
| PLAN | `tdd-planner` | 기능을 사이클로 분해, 계획 파일 작성 |
| RED | `tdd-red` | 실패 테스트 작성 |
| GREEN | `tdd-green` | 통과시키는 최소 구현 |
| REFACTOR | `tdd-refactor` | `/simplify`로 정리 |
| 문서 | `tdd-docs` | 마무리 문서 갱신 |

서브에이전트는 컨텍스트를 공유하지 않는다. **호출할 때마다 테스트 환경(프레임워크·실행 명령·경로), 사이클 번호/제목/설명, 직전 단계 요약을 명시적으로 전달**한다. 진행 상태는 계획 파일 `docs/tdd-plan.md`에 기록해 세션이 끊겨도 남은 사이클부터 재개할 수 있게 한다.

---

## 0. 시작 또는 재개 판정 (한 번만)

`docs/tdd-plan.md`가 이미 있는지 확인한다.
- **있으면 → [R] 재개 모드.** (이전 작업이 중단된 것이므로 다시 계획하지 않는다.)
- **없으면 → [1] 신규 모드.**

---

## 1. 신규 모드 — 브랜치 + 계획

1. 워킹트리가 깨끗한지 확인한다(`git status --porcelain`). 변경이 남아 있으면 멈추고 사용자에게 묻는다 (단계별 커밋 규율이 깨끗한 시작에 의존).
2. **브랜치**: 현재가 기본 브랜치(`master`/`main`/`dev`)면 작업 성격에 맞는 prefix로 `<feat|fix|refactor>/<기능-슬러그>`를 만들어 체크아웃한다. 이미 작업 브랜치면 그대로 사용한다. 정한 브랜치명을 기억한다.
3. **계획**: `tdd-planner`를 띄워 기능 설명과 브랜치명을 전달한다. planner는 기존 테스트를 조사해 프레임워크/컨벤션을 정하고, 기능을 작은 사이클로 분해해 `docs/tdd-plan.md`에 저장하고 보고한다(커밋하지 않는다).
4. 보고된 계획을 **검토**한다(사이클 크기·순서·완전성, 테스트 환경 타당성). 필요하면 조정한다.
5. 계획 파일을 **단독 커밋**: `git add docs/tdd-plan.md && git commit -m "docs(tdd): <슬러그> 계획 수립"`. 다른 변경과 절대 섞지 않는다.

→ [3] 루프로 들어간다.

---

## R. 재개 모드

1. `docs/tdd-plan.md`를 읽어 기능·브랜치·테스트 환경·사이클 목록과 각 상태(`[ ]`/`[x]`)를 복원한다.
2. `git rev-parse --abbrev-ref HEAD`로 현재 브랜치를 확인한다. 계획 파일의 브랜치와 다르면 `git checkout <계획 브랜치>` 한다(브랜치가 없으면 멈추고 불일치를 보고).
3. **중단 지점 진단**: `git status --porcelain`, `git log --oneline -8`. 반쯤 진행된 사이클이 보이면 어느 단계(RED/GREEN/REFACTOR)부터 이어야 할지 판단한다(깔끔히 판단되지 않으면 멈추고 보고). 깨끗하면 첫 번째 `[ ]` 사이클부터 진행한다.

→ [3] 루프로 들어간다 (재계획하지 않는다).

---

## 3. 사이클 반복

다음 `[ ]` 사이클마다 RED → GREEN → REFACTOR를 순서대로 수행한다. 각 워커에 **테스트 환경 + 사이클 제목·설명 + 직전 단계 요약**을 전달한다. 워커가 실패를 보고하면 **즉시 멈추고** 사용자에게 보고한다(계획 파일이 남아 재개 가능).

- **RED** (`tdd-red`) → 실패 테스트를 보고받는다. 새 테스트가 **올바른 이유로 실패**하는지 실제 출력으로 확인한 뒤, 테스트 파일만 커밋: `test(<슬러그>): <제목> (RED)`. (RED는 실패가 정상이다.)
- **GREEN** (`tdd-green`) → 구현을 보고받는다. **포맷·검증 게이트** 통과 시에만 커밋한다: 프로젝트에 포맷터/검증 명령이 있으면 실행하고(CLAUDE.md 참조), 없으면 전체 테스트 스위트를 돌려 **모두 green**을 확인한다. 통과 시 구현 파일만 커밋: `feat(<슬러그>): <제목> (GREEN)`.
- **REFACTOR** (`tdd-refactor`) → 정리 결과를 보고받는다. 변경이 있으면 게이트 통과 후 `refactor(<슬러그>): <제목>` 커밋, 변경이 없으면 GREEN 커밋을 `--amend`해 메시지 끝에 ` (REFACTOR: 변경 없음)`을 덧붙인다 (단계 누락이 아니라 정리할 게 없었음을 히스토리에 남기기 위함).

사이클이 끝나면 계획 파일에서 해당 항목을 `[x]`로 바꾸고 줄 끝에 ` — 커밋: <REFACTOR 또는 amend된 GREEN 해시>`를 기록한 뒤 **단독 커밋**: `docs(tdd): 사이클 N 완료 — <제목>`. 사이클 커밋과 섞지 않는다.

남은 `[ ]`가 있으면 묻지 말고 다음 사이클로 자동 진행한다. 모두 `[x]`면 [4]로 간다.

---

## 4. 마무리 (모든 사이클 완료)

1. **문서** (`tdd-docs`): 한 번 띄운다. 계획 파일과 git log로 작업을 복원해 영향받는 문서·백로그·버그리포트를 갱신해 보고한다(커밋하지 않는다). 메인이 코드와 분리해 커밋: `docs(<슬러그>): 문서 갱신`.
2. **계획 파일 삭제 커밋**: `git rm docs/tdd-plan.md && git commit -m "docs(tdd): 계획 완료 및 정리"`.
3. 사용자에게 보고: 브랜치명, 사이클 수, 각 사이클 한 줄 요약, skip된 REFACTOR(와 이유), 문서 변경 내역. 브랜치는 체크아웃된 채로 두고, 요청 없이는 merge/push하지 않는다.

---

## 규칙

- **실패하는 테스트 없이 구현 코드를 쓰지 않는다.** "그냥 코드부터" 하고 싶어지면 그게 RED부터 쓰라는 신호다.
- **한 사이클 = 한 동작.** 한 사이클에 서로 무관한 assertion이 여럿 필요하면 사이클이 너무 큰 것 → 쪼갠다.
- **모든 커밋은 메인이 만든다.** 서브에이전트는 디스크만 바꾸고 보고만 한다.
- **계획 파일은 항상 단독 커밋.** 코드 커밋과 절대 섞지 않는다.
- **신뢰하지 말고 검증한다.** 단계 사이마다 실제 테스트 출력으로 red/green을 확인한다.
- **무관한 버그 발견 시**: 그 자리에서 고치지 않는다. 프로젝트에 버그 기록 문서가 있으면(CLAUDE.md 참조) 발견 맥락과 함께 별도 커밋으로 기록한 뒤 진행한다.
