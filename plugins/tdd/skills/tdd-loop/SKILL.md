백로그를 자동으로 소진하는 오케스트레이터다. 작업 범위: **$ARGUMENTS**

핵심 원리: **항목 하나 = 의미론적 브랜치 하나 = `--no-ff` 머지 하나.** 단, 모든 작업은 BASE가 아니라 **통합 브랜치** 위에 누적되고, 전체 계획이 끝났을 때 한 번만 BASE로 머지된다. 진행 상태는 계획 파일에 기록해 중간에 끊겨도 재개한다.

각 항목의 RED/GREEN/REFACTOR와 단계별 커밋은 `/tdd`에 위임한다. 이 스킬은 **작업 목록 수립 · 계획 파일 관리 · 통합 브랜치 분기/머지 · 백로그 갱신 · 루프 제어 · 재개**만 담당한다. 이 흐름이 전부이며 계획·검수를 위한 별도 에이전트를 추가로 띄우지 않는다(각 항목의 계획은 `/tdd` 안의 PLAN 단계가 맡는다).

용어:
- `BASE`: 스킬 호출 시점의 브랜치(`master`, `dev` 등). 최종 산출물의 머지 목적지.
- `INTEG`: 이번 루프의 통합 브랜치(`loop/<슬러그>`). 모든 항목 브랜치가 여기로 머지된다.
- **작업 출처**: 구현할 항목이 적힌 곳. 아래 0-1에서 정한다.
- **검증**: 프로젝트가 정의한 검증 명령(README, CLAUDE.md 같은 지침 문서, package.json scripts, Makefile, CI 설정 등에서 찾는다), 없으면 전체 테스트 스위트. 아래 "검증"은 이를 가리킨다.

## 계획 파일 (repo 밖, 커밋하지 않음)

- 상태 폴더: `<홈>/.claude/tdd-state/<repo 루트 폴더명>/`. repo 루트는 `git rev-parse --show-toplevel`. 없으면 만든다. **홈 경로는 시작할 때 한 번 절대 경로로 해석**해 두고(POSIX는 `$HOME`, Git Bash는 `cygpath -m "$HOME"`, PowerShell은 `$HOME`) 이후 도구 호출에 그 값을 그대로 쓴다.
- 계획 파일: `<상태 폴더>/loop/<슬러그>.md`. 이번 루프 동안만 존재하며 마지막에 삭제된다. 커밋하지 않는다.
- `/tdd`의 계획 파일은 같은 상태 폴더의 `tdd/` 아래에 항목 브랜치별로 생기고, `/tdd`가 알아서 관리한다.
- 계획 파일의 `저장소:`(repo 루트 절대 경로)가 현재 repo와 같은 파일만 이 repo의 것으로 본다.

## 0. 시작 또는 재개 판정 (한 번만)

상태 폴더 `loop/`에서 `저장소:`가 현재 repo인 계획 파일을 찾는다.
- **하나도 없으면 → 신규 모드 (0-1).**
- **하나면 → [R] 재개 모드.** 단, `$ARGUMENTS`의 범위가 계획의 `범위:`와 명백히 다르면 멈추고 한 번만 묻는다(이어서 할지, 새로 시작할지).
- **둘 이상이면** 현재 브랜치가 `INTEG`이거나 항목 브랜치로 등장하는 파일을 고른다. 하나로 정해지지 않으면 멈추고 어느 것을 이을지 묻는다.

### 0-1. 신규 모드 준비

1. **BASE 고정**: `git rev-parse --abbrev-ref HEAD`를 읽어 `BASE`로 기억한다.
2. **워킹트리 청결**: `git status --porcelain`이 비어 있어야 한다. 변경이 있으면 멈추고 보고한다(커밋/스태시 여부 질문).
3. **작업 출처 결정**:
   - `$ARGUMENTS`에 구현할 항목이 직접 적혀 있으면(문장, 이슈 번호, 파일 경로 등) 그것이 출처다.
   - 아니면 프로젝트 지침(CLAUDE.md, README 등)이 백로그 위치를 정해 두었는지 찾는다. 파일이면 읽고, 이슈 트래커면 해당 CLI/도구(`gh` 등)로 조회한다.
   - 둘 다 없으면 멈추고 무엇을 구현할지 묻는다(백로그를 임의로 만들지 않는다).
4. **범위 해석**: `$ARGUMENTS`를 해석한다.
   - **개수형**("5개", "3개 항목") → 그 개수만큼 담는다.
   - **기능 지정형**("xx 기능까지") → 해당 기능을 포괄하는 항목들을 담는다.
   - **전부**("백로그 전부", "다 끝낼 때까지") → 실행 가능한 모든 항목을 담는다.
   - **항목 직접 지정** → 지정된 항목만 담는다.
   - **생략/빈 값** → **자체 결정.** 백로그의 우선순위 상단(위에 있을수록, 또는 트래커의 우선순위·라벨 순)에서 한 번의 루프로 무리 없이 끝낼 응집된 범위(보통 서로 연관된 상위 2~4개)를 스스로 정하고, 범위와 근거(속도/종속/임팩트)를 한 줄로 알린 뒤 그대로 진행한다(승인 대기하지 않는다).
   - 명시됐으나 해석이 모호하면 멈추고 한 번만 확인한다.
5. 작업 출처에서 범위 항목을 추리고, 각 항목의 상세(동기·범위·메모 등)를 가져온다.
   - **제외**: 보류·미확정·장기 검토 표시 항목.
   - **차단 항목**: 합리적 기본 결정이 가능하면 그 결정을 내려 포함하고, 진짜 불가능하면 빼고 마지막 요약에 남긴다.

### 0-2. 통합 브랜치 생성 + 계획 파일 작성

1. 범위를 대표하는 슬러그로 `INTEG = loop/<슬러그>`로 둔다.
2. `git checkout <BASE>` 확인 후 `git checkout -b <INTEG>`.
3. 상태 폴더의 `loop/` 아래에 계획 파일 `<슬러그>.md`를 작성한다.

   ```markdown
   # TDD Loop 계획

   - 저장소: <repo 루트 절대 경로>
   - 베이스 브랜치: <BASE>
   - 통합 브랜치: <INTEG>
   - 범위: <원문 $ARGUMENTS 또는 자체 결정 요약>
   - 작업 출처: <파일 경로 / 트래커 / 인자>

   ## 항목

   - [ ] 1. <기능 한 문장 요약> — 출처 항목: <제목 또는 이슈 번호> — 브랜치: <feat|fix|refactor>/<슬러그> — 머지: -
   - [ ] 2. <기능 한 문장 요약> — 출처 항목: <...> — 브랜치: <...> — 머지: -

   ## 발견한 이슈
   (없음)
   ```

   - 각 항목은 `/tdd`를 **한 번** 호출해 끝낼 수 있는 단위로 쪼갠다. 항목 수 = tdd 호출 횟수.

→ [1] 루프로 들어간다. (계획 파일은 커밋하지 않는다.)

---

## R. 재개 모드

1. 계획 파일을 읽어 `BASE`, `INTEG`, 범위, 항목 목록과 각 상태를 복원한다.
2. `INTEG` 브랜치가 없으면 멈추고 불일치를 보고한다. 있으면 현재 브랜치가 항목 브랜치(계획 파일의 브랜치명 중 하나)가 아닌 한 `git checkout <INTEG>`.
3. **중단 지점 진단**: 첫 번째 `[ ]` 항목(들)에 대해 아래를 위에서부터 판정한다.
   1. `git log <INTEG> --merges --format=%s`에 그 항목 브랜치의 머지 커밋이 있으면 이미 머지된 것이다. 머지 해시만 계획 파일에 `[x]`로 기록하고 다음 `[ ]` 항목으로 간다(1-4가 빠졌다면 1-4부터 이어 간다).
   2. 항목 브랜치가 있고 INTEG보다 앞선 커밋이 있으며 해당 브랜치의 `/tdd` 계획 파일(`tdd/`)이 없으면, `/tdd`는 끝난 것이다. 1-3(머지)으로 간다.
   3. 항목 브랜치가 있고 `/tdd` 계획 파일이 있으면 `/tdd`가 중단된 것이다. 그 브랜치를 체크아웃한 채 1-2로 가서 `/tdd`의 재개 모드가 받게 한다.
   4. 항목 브랜치가 없으면 1-1부터 시작한다.
   - 위로 판정되지 않거나 서로 어긋나면(`git status --porcelain`, `git log --oneline -10`, `git branch --list '*/*'`로 확인) 멈추고 보고한다.

→ [1] 루프로 들어간다 (재계획하지 않는다).

## 1. 루프 (모든 `[ ]` 항목이 `[x]`가 될 때까지)

다음 `[ ]` 항목마다 아래를 순서대로 수행한다. 항상 `INTEG` 위에서 시작한다.

### 1-1. 항목 브랜치 분기
`git checkout <INTEG>` 확인 후 계획 파일의 브랜치명으로 `git checkout -b <항목-브랜치>`. (이미 있으면 재개 상황이므로 체크아웃만 한다.)

### 1-2. 구현 위임
`/tdd <해당 항목의 기능 요약 한 문장> (tdd-loop 하위 호출: 발견한 이슈는 이관하지 말고 보고만 한다)`을 호출한다. 현재 항목 브랜치 위이므로 tdd가 이 브랜치에서 RED→GREEN→REFACTOR를 돌리고 단계별 커밋한다.
- **tdd가 실패를 보고하면** 즉시 루프를 멈추고 현재 상태와 함께 보고한다. 머지하지 않는다(계획 파일이 남아 재개 가능).
- tdd가 보고한 `발견한 이슈`는 이 루프의 계획 파일 `## 발견한 이슈`에 옮겨 적는다.

### 1-3. 통합 브랜치로 머지
`git checkout <INTEG>` 후 `git merge --no-ff <항목-브랜치> -m "merge: <기능 요약> (<항목-브랜치>)"` (프로젝트 커밋 컨벤션과 기존 `git log`의 언어를 따른다. 판단할 수 없으면 기능 설명의 언어).
- **충돌 시**: 자동 해소하지 말고 `git merge --abort` 후 멈추고 보고.
- 머지 후 **검증**으로 통합 상태가 green인지 확인한다. 실패하면 멈추고 보고.
- 통과 시 항목 브랜치 삭제: `git branch -d <항목-브랜치>`.

### 1-4. 백로그 갱신
프로젝트 지침이 백로그 갱신 방식을 정해 둔 경우에만 완료 항목을 그 방식으로 처리한다(파일이면 해당 항목을 지우거나 완료 표시, 트래커면 이슈 닫기 등). 정해 둔 방식이 없으면 건드리지 않고 최종 요약에만 남긴다. 파일을 고쳤다면 이 변경만 `INTEG` 위에서 별도 커밋한다.

### 1-5. 계획 파일 갱신
해당 항목을 `[x]`로 바꾸고 `머지:`에 1-3의 머지 커밋 해시를 기록한다(파일만 고치고 커밋하지 않는다).

### 1-6. 다음 항목
남은 `[ ]`가 있으면 **묻지 말고** 1-1로 돌아가 자동 진행한다. 모두 `[x]`면 [2]로 간다.

## 2. 마무리 (모든 항목 완료)

1. **발견한 이슈 이관**: 계획 파일의 `## 발견한 이슈`를 읽어 둔다. 프로젝트 지침이 버그 기록 방식을 정해 두었다면 그 방식으로 옮긴다(파일이면 `INTEG` 위에서 별도 커밋). 정해 둔 것이 없으면 이슈를 새로 만들지 않고 종료 요약에만 남긴다.
2. **BASE로 머지**: `git checkout <BASE>` 후 `git merge --no-ff <INTEG> -m "merge: <범위 요약> tdd-loop 완료 (<INTEG>)"`. 충돌 시 `git merge --abort` 후 멈추고 보고. 이 스킬은 의도적으로 결과를 BASE에 로컬 머지한다(push는 하지 않는다).
3. 머지 후 **검증**으로 최종 green을 확인한다. 실패하면 멈추고 보고.
4. 통과 시 통합 브랜치 삭제: `git branch -d <INTEG>`. 위에서 읽어 둔 이슈 목록을 기억해 둔 채 계획 파일을 삭제한다(상태 폴더가 비면 폴더도).

## 3. 부수 규칙

- **무관한 버그 발견 시**: 그 자리에서 고치지 않는다. 계획 파일의 `## 발견한 이슈`에 발견 맥락과 함께 한 줄 추가하고 본 작업을 계속한다. 마무리 [2]의 이슈 이관 규칙으로 처리한다.
- 백로그 파일 변경 커밋은 **항상 INTEG 위에서만** 일어난다. 항목 브랜치나 BASE에서 건드리지 않는다.
- 루프는 다음 경우에만 멈춘다: 전체 완료, 실행 가능 항목 없음, tdd 실패, 머지 충돌, 검증 실패, 진짜 차단 항목, 재개 지점 불명확, 작업 출처를 알 수 없음.

---

## 4. 종료 요약

- 완료한 항목 목록과 각 `--no-ff` 머지 커밋 해시.
- 건너뛴/차단된 항목과 이유.
- 계획 파일의 `발견한 이슈` 목록.
- 종료 사유(전체 완료 / 항목 소진 / 실패로 중단 — 중단이면 재개 방법: 같은 스킬 재호출 시 계획 파일로 이어감).
- 현재 브랜치가 `BASE`이고 워킹트리가 깨끗한지, 통합 브랜치·계획 파일이 정리됐는지.
