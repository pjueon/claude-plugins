# language-guideline 스킬

프로젝트의 성격과 글의 목적(기술 문서, 비즈니스 보고서, 메신저 대화, 블로그, 소설/창작 등)에 맞춰, `../../shared/`의 마스터 규칙을 기반으로 **가장 필요한 30~50줄 내외의 정제된 맞춤형 언어 지침**을 동적으로 생성하고 배치합니다.

---

## 1. 다양한 문맥별 조절 원칙 (Context Adaptation)

기본적인 탈-AI 코어 원칙(번역투 조사 직역 제거, 공허한 찬사 배제, 의미 보존)은 공통으로 지키되, **글의 문맥에 따라 규칙을 유연하게 조절**합니다:

* **기술 문서 / 가이드 / 매뉴얼 / 버그 리포트**:
  - 소제목 명사구 종결 엄격 적용 (질문형/서술형/대구형 금지).
  - 어설픈 비유("허리/심장/아픔") 및 알고리즘 의인화("욕심/밀어낸다") 엄격 배제.
  - 수식 및 기호 조사의 발음 소리 기준 결합 준수.
  - 합쇼체('~합니다') 또는 평서체('~다').
* **비즈니스 / 기획서 / 보고서 / 업무 이메일**:
  - 두괄식(BLUF): 첫 문장에 용건과 핵심 요구사항 제시.
  - 모호한 완곡어법(Hedging)과 상습적 사과 표현 배제, 명확한 Action Item 서술.
  - 정중하고 단정한 합쇼체('~합니다', '~해 주시기 바랍니다').
* **사내 메신저 / 슬랙 / 대화 초안**:
  - 소제목을 쓰지 않고 첫 줄에 핵심 요점 제시.
  - 지나치게 경직된 공문서 말투를 피하고 부드러운 해요체('~해요')와 자연스러운 구어 호흡 적용.
* **블로그 / SNS / 영상 대본**:
  - 도입부에서 흥미를 유발하되 AI식 낚시성 클리셰 배제.
  - 호흡 변주(Burstiness): 아주 짧은 단문과 설명 복문을 섞어 리듬감 형성.
  - 필자의 주관과 관점을 적극 살림.
* **소설 / 에세이 / 스토리텔링**:
  - 문학적 비유, 인물의 감정선, 의인화는 자유롭게 허용.
  - 단, AI 특유의 진부한 클리셰("새로운 지평을 열다", "가슴이 벅차올랐다")만 선별 제거.

## 2. 지침 생성 절차

### 단계 1: 맥락 및 파라미터 파악
사용자의 프롬프트와 프로젝트 환경에서 다음을 자동으로 파악합니다:
1. **타깃 위치**:
   - 기본값: 프로젝트 루트의 `CLAUDE.md` (`## 작문 및 언어 원칙` 섹션으로 추가/치환).
   - 지정 파일: 사용자가 요청한 파일 (예: `shared/writing-style.md`, `.claude/rules.md`).
   - 스킬 주입: 특정 스킬 작성을 위한 요청인 경우 해당 스킬의 문체 지침 섹션으로 출력.
2. **문맥 및 언어**:
   - 한국어(기본) vs 영어 vs 다국어.
   - 글의 목적(기술, 비즈니스, 메신저, 블로그, 창작 등).
3. **사용자 특별 요청**:
   - 예: "친절하고 쉬운 설명", "은유는 적당히 허용", "영어로 간결하게".

> **질문 가드레일**: 요구사항이 명확하면 추가 질문 없이 즉시 생성하여 파일에 반영하십시오. 문맥이나 타깃 위치가 모호할 때만 1~2개 선택지로 가볍게 질문하십시오.

### 단계 2: 마스터 지침 기반 동적 추출 (Distillation)
1. `../../shared/core-rules.md`, `../../shared/korean-rules.md`(또는 `english-rules.md`)에서 필수 규칙 선택.
2. 전역 오답 노트(`~/.claude/writing-feedback.md`)가 존재하면, 사용자가 싫어하는 표현 규칙을 함께 반영.
3. **사용자 요청 최우선 (User Precedence)**: 사용자가 코어 규칙과 다른 방향(예: "은유 적극 허용", "질문형 제목 사용", "특정 번역투 허용")을 요구한 경우, 기본 코어 규칙을 배제하고 **사용자의 요구사항을 최우선으로 반영**하여 지침을 구성.
4. 대상 문맥의 특성에 맞게 가감(조절)하여 30~50줄 분량으로 압축.

### 단계 3: 파일 반영 및 완료 보고
- 타깃 파일에 단정하게 마크다운 블록으로 반영합니다.
- 플러그인이 만든 블록임을 `<!-- human-language:start -->` ~ `<!-- human-language:end -->` 주석으로 감쌉니다. 재실행 시 이 마커 안쪽만 교체합니다.
- 마커가 없는 같은 이름의 기존 섹션(사용자가 직접 쓴 것)이 있으면 덮어쓰지 말고, 변경안을 보여주고 병합 방식을 한 줄로 묻습니다.
- 반영된 핵심 규칙 요약과 파일 위치를 사용자에게 간결히 보고합니다.

## 3. 생성 결과물 예시 (기술 문서 문맥 기준)

```markdown
## 작문 및 언어 원칙

이 규칙 자체를 답변에 언급하지 마십시오.

### 1. 구조 및 제목
- 첫 문단에 핵심 결론을 바로 제시하십시오. 과정 중계("지금부터 ~를 알아보겠습니다")와 불필요한 결론 요약을 배제하십시오.
- 소제목(h2, h3)은 반드시 명사구로 종결하십시오. (질문형/서술형/대구형/접속사 시작 금지)
- 단계별 제목은 한 형태(전부 "~하기" 또는 전부 명사구)로 통일하십시오.

### 2. 번역투 및 피동 해체
- 조사 직역(~에 대해, ~를 통해, ~에 있어서)을 금지합니다. 목적어(~을/를)나 수단(~로)으로 직결하십시오.
- 이중 피동(~되어지다)을 금지하고 능동형(된다, 보인다)으로 서술하십시오.
- '가지고 있다' 대신 '~이 있다', '~를 갖추다'를 사용하십시오.

### 3. 어설픈 비유 및 의인화 배제
- 문서 은유("교재의 허리/심장/씨앗", "개발자의 아픔", "맛보기", "손에 쥐는 것")를 쓰지 말고 개념을 직접 서술하십시오.
- 알고리즘 의인화("함수가 욕심을 낸다", "밀어낸다", "알아서 허락한다")를 금지하고 객관적 메커니즘으로 서술하십시오.

### 4. 표기 및 수식
- 수식과 기호 조사는 철자가 아닌 '읽는 소리' 기준으로 결합하십시오. (예: $x^{(3)}$은, int는)
- 두 식이 더해져 사라지는 것은 '약분'이 아니라 '상쇄'입니다. 사이시옷('최댓값', '최솟값')을 준수하십시오.
- 어체는 합쇼체('~합니다')로 일관되게 유지하십시오.
```
