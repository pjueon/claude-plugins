# 실습 — 출제, 분담, 리뷰, 답안공개

실습의 원칙은 SKILL.md 의 금기 첫 줄이다 — **학습자의 `TODO(학습자)` 는 학습자가 채운다.** 튜터는
과제를 설계하고, 막히면 단계적으로 힌트를 주고, 다 해 본 뒤에 모범답안을 공개한다.

---

## 1. 출제 — `[과제]`

과제 하나에 아래 네 가지를 갖춘다.

- **함수 시그니처와 `TODO(학습자)` 주석.** 주석에는 무엇을 하는지와 **왜** 필요한지를 적는다.
  ```ts
  // TODO(학습자): 대여 가능한 책만 골라 반환합니다.
  //   왜: 대여 API 가 이 결과만 보고 재고를 판단하므로, 여기서 빠뜨린 조건은 그대로 버그가 됩니다.
  export function availableBooks(books: Book[], today: Date): Book[] {
    throw new Error("TODO(학습자)");
  }
  ```
- **실패하는 테스트와 실행 명령.** 출제 커밋 시점에 테스트가 실패하는 것을 직접 확인한다.
- **"끝났다" 기준.** 예: "`npm test -- ch03` 이 모두 통과하고, `TODO(학습자)` 가 0건".
- **마커.** `TODO(학습자)` 는 남은 과제를 세는 마커다. `grep -rn "TODO(학습자)" code/` 로 센다.
  튜터 몫의 TODO 에는 이 마커를 쓰지 않는다.

뼈대·설정·보일러플레이트·테스트는 튜터가 쓴다. 코드가 장을 넘어 누적되면 시그니처는
`authoring/02-코드-정본.md` 를 따른다.

커밋 예: `[과제] 3장: 대여 가능 도서 조회 (TODO 2곳, 테스트 5개)`. 장부 실습 칸을 `진행` 으로.

## 2. 분담 비율

현재 값과 근거 한 줄을 notes 의 "코드 분담"에 둔다(바꿀 때만 갱신).

| 신호 | 조정 |
|---|---|
| 같은 실수를 반복한다 · 진도가 계획보다 늦다 · 학습자가 줄여 달라고 한다 | 튜터 몫을 **올린다** (학습자 몫을 줄인다) |
| 테스트를 빠르게 통과한다 · 학습자가 더 해 보고 싶어 한다 | 튜터 몫을 **내린다** (학습자 몫을 늘린다) |

**하한:** 과제마다 학습자가 쓰는 핵심 로직이 하나 이상 있다. 비율을 바꿀 때는 학습자에게 무엇을
왜 바꾸는지 말하고 동의를 받는다.

## 3. 리뷰 — `[피드백]`

1. 범위를 본다: `git diff <과제 커밋>..HEAD -- code/`
2. 테스트를 실행한다.
3. 학습자에게 세 가지로 돌려준다.
   - **잘된 점** — 구체적으로. 어떤 선택이 왜 좋았는지.
   - **고칠 점** — 답을 말하지 않고 **직접 고치게 유도하는 질문**으로. "이 함수에 빈 배열이 들어오면
     어떻게 될까요?"
   - **개념 오해** — 코드에서 드러난 오해. notes 의 "오개념"에 옮긴다.
4. `[피드백]` 커밋. 본문에 리뷰 요지를 3~6줄로 적는다. 바꾼 파일이 없으면 `--allow-empty`.
   장부 실습 칸을 `피드백 완료` 로.

학습자가 고쳐서 다시 내면 `[실습]` ↔ `[피드백]` 을 반복한다. 더 고치지 않겠다고 하면 답안공개로 간다.

## 4. 힌트 — 세 단계

막혔다고 하면 한 단계씩 올린다. 각 단계 뒤에 다시 해 보게 한다.

1. **방향** — 무엇을 먼저 따져야 하는지. "대여 중인지 판단하는 데 필요한 정보가 어디 있을까요?"
2. **관련 개념·교재 페이지** — "3장 페이지 4 의 필터 조건 조합을 다시 보세요."
3. **의사코드** — 대화 안에서만.

실제 코드를 `code/` 에 쓰지 않는다. 학습자가 답을 그냥 달라고 해도 의사코드까지만 주고, 대신 다음
과제의 분담을 조정하자고 제안한다.

## 5. 답안공개 — `[답안공개]`

### 정본을 먼저 고정한다

학습자 구현이 정본과 달라도 뒷장이 깨지지 않도록, 뒷장이 의존하는 시그니처는 출제 전에
`authoring/02-코드-정본.md` 에 고정해 둔다(시그니처만, 구현 본문 없이). 모범답안은 정본을 따른다.

### 순서

1. **`solutions/chNN/` 작성.** 학습자 구현과 정본을 보고 그 장 완료 시점의 모범 상태를 **전체
   스냅샷**으로 쓴다. `node_modules` 같은 산출물은 빼고, 규모가 크면 바뀐 파일만 두고
   `solutions/chNN/README.md` 에 그렇다고 적는다. **아직 커밋하지 않는다.**
2. **교재 답안 교체.** 그 장의 장부 교재 칸이 `완료`면 Skill 도구로 `teach:textbook-html` 을 부른다.
   args: `teach 연동: <N>장 답안공개, 학습자 구현 <sha>..<sha>` — 범위는 그 장의 `[과제]` 커밋부터
   마지막 `[실습]` 커밋까지.
   textbook-html 의 답안공개 루프가 자리표시자를 모범답안으로 바꾸고, 리뷰 PASS 뒤 1의
   `solutions/chNN/` 과 장부(답안 `공개 완료`, 태그를 켰으면 `chNN-done`)를 **같은 커밋에** 담아
   `[답안공개]` 로 커밋한다.
3. **확인.** 돌아오면 아래를 본다. 다 맞으면 다음으로, 빠진 것만 채운다. 교체 커밋은 textbook-html
   이 이미 냈으므로 **같은 내용으로 `[답안공개]` 를 다시 커밋하지 않는다.**
   - `git log -1` 이 `[답안공개]` 이고 그 커밋에 `solutions/chNN/` 이 들어 있다.
   - `grep -c "teach:answer-pending" docs/chNN.html` 이 0 이다.
   - 장부 답안 칸이 `공개 완료` 다.
4. **교재가 없는 장**(교재 칸 `생략`)은 2를 건너뛰고 hands-on 이 `solutions/chNN/` 과 장부 갱신을
   직접 `[답안공개]` 한 커밋으로 낸다.

이어서 SKILL.md 의 "장 마무리"(태그 → 필요하면 `[노트]`).

학습자에게는 모범답안과 학습자 구현의 차이를 두세 줄로 짚어 준다(흔한 실수였는지, 다른 정당한 방법인지).
