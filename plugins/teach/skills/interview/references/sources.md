# 대상 판정과 자료 준비

요청을 보고 아래 셋 중 하나로 정한다. 둘이 섞이면(예: "이 책 3장까지, TypeScript 코드로") 문헌 범위(A)를
기준으로 하고 코드 문항은 B 의 규칙을 따른다. 판정이 모호하면 0의 확인 메시지에서 함께 묻는다.

| 판정 | 신호 | 문제의 근거 |
|---|---|---|
| **A 문헌 범위** | 파일 경로·첨부(PDF·HTML·md·epub 변환본), "~장까지 읽었어", 논문 제목+파일 | 그 파일의 해당 범위 |
| **B 진도 기반 실력 테스트** | 언어·라이브러리·도구 이름 + 진도("~까지 했어", "입문 수준") | 진도 안의 문법·API |
| **C 개념** | 개념·기술 이름만("가우시안 스플래팅에 대해 질문해봐") | 모델 지식(+ 웹 확인) |

---

## A. 문헌 범위

1. **파일을 찾는다.** 경로가 없으면 현재 폴더에서 `Glob` 으로 후보를 찾아 확인한다. 파일이 없으면
   멈추고 경로를 묻는다 — 기억에 기대어 책 내용을 지어내지 않는다.
2. **범위를 쪽 번호로 확정한다.** 목차(PDF 는 앞쪽 몇 쪽, HTML 은 제목 구조)에서 "3장까지"가 몇 쪽인지
   찾는다. 인쇄 쪽 번호와 PDF 쪽 번호가 다르면 둘 다 적는다(질문·피드백에는 인쇄 쪽 번호를 쓴다).
3. **핵심 목록을 만든다.** 범위를 읽고 `개념 — 원문 위치 — 한 줄 요지` 목록(15~30줄)을 만든다.
   - 범위가 길면(대략 40쪽 이상, 또는 여러 파일) Agent(`model: sonnet`)에게 범위를 나눠 읽혀 이 목록만
     돌려받는다. 원문을 대화에 옮겨 오지 않는다.
   - Read 로 PDF 를 읽을 때는 `pages` 로 20쪽씩 나눈다.
4. **문항은 이 목록에서만 낸다.** 채점 기준의 요점마다 원문 위치를 붙이고, 피드백에서 "p.42 의 그림
   3.4 를 다시 보세요"처럼 가리킨다. 저자의 용어와 표기를 그대로 쓴다.
5. 범위에 연습문제가 있으면 그대로 내지 않는다(학습자가 이미 풀었을 수 있다). 같은 개념을 다른 상황에
   적용하게 바꿔 낸다.

## B. 진도 기반 실력 테스트

1. **진도를 상한으로 둔다.** "제네릭까지"면 그 뒤에 배우는 문법(예: 조건부 타입)은 문항·정답 코드
   모두에 쓰지 않는다. 진도의 기준이 되는 자료(공식 핸드북 목차, 교재)가 있으면 그 순서를 따르고,
   없으면 0의 확인 메시지에 "이 범위로 이해했습니다: …"라고 적어 확인받는다.
2. **실행 환경을 확인한다.** 그 언어를 실행할 수 있는지 `command -v` 로 본다(예: TypeScript 는
   `node`·`npx tsc`, Python 은 `python3`). 설치는 하지 않는다. 학습자 PC 에 영향을 주는 설치가
   필요하면 묻는다.
   - 실행할 수 없으면 코드 작성·빈칸·버그 문항은 "설명형"(코드 읽기·동작 설명·출력 예측을 말로)으로
     바꾸고, 그렇게 바꿨다고 알린다. 출력 예측 문항의 정답도 실행할 수 없으면 내지 않는다.
3. **난이도 사다리** — 정의·문법 읽기 → 짧은 코드 동작 설명 → 빈칸 채우기 → 버그 찾기 → 작은 함수
   구현 → 설계·트레이드오프. 첫 문항은 진도의 중간 정도에서 시작한다.

## C. 개념

1. **채점 기준을 쓰기 전에 사실을 확인한다.** 확신이 높은 핵심(정의, 동작 원리, 대표적 장단점)만
   문항으로 쓴다. 수치·연도·논문별 세부 차이처럼 틀리기 쉬운 것은 WebSearch 로 확인한 뒤에만 쓰고,
   확인하지 못했으면 묻지 않는다.
2. **수준의 단서를 찾는다.** 학습자가 배경(전공, 써 본 경험)을 말하지 않았으면 0의 워밍업으로 진단한다.
3. **개념 지도를 짧게 만든다.** 선행 개념 → 핵심 → 응용·비교 순서로 5~8개를 메모한다. 문항은 이
   순서를 따라 깊어지고, 막히면 선행 개념으로 내려간다.
