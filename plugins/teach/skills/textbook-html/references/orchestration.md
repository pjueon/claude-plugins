# 집필 오케스트레이션

커리큘럼 확정 뒤의 집필은 **메인이 오케스트레이터**다. 장 본문은 직접 쓰지도 리뷰하지도 않는다.

| 역할 | 누가 | 하는 일 |
|---|---|---|
| 오케스트레이터 | 메인 | 지시서 작성, 장부 관리, 판정 처리, 병렬 판단, **커밋**, 보고 |
| 집필 | `teach:textbook-writer` | 장 하나 집필·자체 점검·지적 반영 |
| 리뷰 | `teach:textbook-reviewer` | 독립 검수, PASS/FIX 판정 (수정 안 함) |

기획·커리큘럼·골격 세우기(SKILL.md 절차 1~3)는 사용자와 대화가 필요하므로 메인이 직접 한다.

## 진행 장부 — `authoring/03-진행-장부.md`

서브에이전트는 매번 빈 머리로 시작한다. 장 사이의 약속은 기억이 아니라 파일로 넘긴다.
골격 세우기 때 오케스트레이터가 만든다.

```markdown
# 진행 장부
## 미결 약속   | 약속 | 한 장 | 갚을 장 |   (갚은 장이 줄을 지운다)
## 용어·기호   | 용어/기호 | 정의한 장·페이지 | 한 줄 뜻 |
## 장별 기록   ### N장 — 제목 (커밋 해시): 페이지 목록 · 뒷장이 알아야 할 이름/시그니처 · 커리큘럼과 달라진 점
## 장별 상태   | 장 | 교재 | 실습 | 답안 | 태그 |
```

`## 장별 상태` 는 hands-on 연동 교재의 표다. 칸 값은 다음으로 고정한다.

- 교재: `해시` / `생략`
- 실습: `대기` / `진행` / `피드백 완료` / `없음`
- 답안: `즉시 동봉` / `공개 대기` / `공개 완료(해시)`
- 태그: `chNN-done` / `—`

"교재" 칸은 오케스트레이터가, "실습"·"답안"·"태그" 칸은 hands-on 이 갱신한다. 이 표가 없는 기존 교재는 답안 "즉시 동봉"으로 간주한다.

순차 모드에서는 집필자가, 병렬 모드에서는 오케스트레이터가 반영한다. 장부는 그 장의 커밋에 포함한다.

## 장 하나의 루프 (기본: 순차)

1. 지시서를 써서 집필 에이전트를 호출한다.
2. 집필 보고를 받아 리뷰 에이전트(새 인스턴스)를 호출한다.
3. PASS → 4. FIX → BLOCK 목록 **원문**을 집필 에이전트(수정 모드)에 전달하고 재리뷰. 최대 2회, 그래도 FIX 면 멈추고 사용자에게 보고한다.
4. 오케스트레이터가 probe 를 한 번 확인하고 **커밋**한다.
5. 한 줄 보고(장·페이지 수·리뷰 라운드·커밋) 후 다음 장으로 이어 간다. "한 장 쓰고 멈춰"라고 했을 때만 멈춘다. hands-on 이 부른 경우에는 지시된 장만 처리하고 멈춘다.

R8 은 리뷰 PASS 로 충족한다. 사용자에게 묻는 것은 2라운드 실패, 커리큘럼 수정이 필요한 발견, 정본 변경뿐이다.

**지시서에 담을 것:** skill·교재 루트·브라우저 절대경로, 장 번호, 모드, 병렬 여부, 사용자가 따로 정한 사항, (수정) BLOCK 원문, (리뷰) 집필 보고 원문. 장 내용은 옮겨 적지 않는다 — 에이전트가 커리큘럼을 읽는다.

**커밋:** 장 하나 = 커밋 하나(`docs/chNN.html`, `book.js` 변경분, 장부). 한국어 메시지에 `[교재]` 접두어, 예: `[교재] 3장 집필: 정규화와 키 설계 (12페이지)`. 런타임(`book.css`/`book.js` 로직) 수정은 별도 커밋으로 먼저 낸다.

## 병렬화 — 확실히 이득일 때만

순차가 기본인 이유는 "N장에서 다룬다" 같은 약속과 앞장 참조가 어긋나지 않게 하려는 것이다. 아래를 **모두** 만족하면 묶어서 병렬로 쓴다.

1. **의존 없음** — 묶음 안 장끼리 "앞장에서 받는 것"이 겹치지 않는다. 묶음 밖 앞선 장은 이미 커밋·장부 반영됐다.
2. **약속이 고정됨** — 묶음 안 장끼리 주고받을 것이 없거나, 이름과 형태까지 커리큘럼·장부에 적혀 있다.
3. 코드 누적 교재면 **정본이 있다.**
4. **이득이 크다** — 장당 대략 8페이지 이상이고 둘 이상이다.

개념의 허리 장, 앞장 코드를 이어받는 장은 묶지 않는다. 판단이 서지 않으면 순차로 한다. 병렬이면 묶음과 근거를 한두 줄로 알리고 진행한다.

**절차:** 집필 에이전트를 한 번에 병렬 호출(지시서에 `병렬 모드`; `book.js`·장부는 건드리지 않고 보고로 반환) → 오케스트레이터가 `TERMS`·`BOOK`·장부를 한 번에 합침(용어 충돌은 여기서 잡아 해당 장을 수정 모드로 되돌림) → 장별 리뷰 후 묶음 **교차 검수** 1회 → 장 번호 순으로 장마다 커밋. 교차 검수에서 BLOCK 이 반복되면 남은 장은 순차로 돌아간다.

## 답안공개 루프

후공개 장(`details.fold answer` 가 자리표시자인 장)에 학습자의 구현이 끝난 뒤 모범답안을 넣는 루프다. 호출 args 는 `teach 연동: <N>장 답안공개, 학습자 구현 <sha>..<sha>`. 이 루프도 지시된 장만 처리하고 멈춘다.

1. 지시서에 `답안공개` 모드, 장 번호, 학습자 구현 커밋 범위, `solutions/chNN/` 경로를 담는다.
2. writer 가 자리표시자만 실제 답안으로 교체한다. 학습자 구현을 읽고 흔한 실수를 짚으며 정본과 비교한다. 학습자 구현은 Read 만 하고 고치지 않는다.
3. reviewer 가 축약 점검을 한다 — 기계 점검, R7 공개 후 기준(마커 0건·답안 존재·`solutions/chNN/` 과 일치), 코드 사실성, 행 번호.
4. PASS 면 오케스트레이터가 `[답안공개]` 커밋을 낸다. `solutions/chNN/` 은 hands-on 이 미리 써 둔 것을 같은 커밋에 넣는다.
5. 장부의 답안 칸을 `공개 완료(해시)` 로 바꾼다.

## 기존 장의 문체 교정 패스

완성된 교재에 "한국어가 어색하다 / 번역투·AI 같다 / 읽기 어렵다" 피드백이 오면 장 단위 루프를 이렇게 돌린다.

1. **기준을 먼저 고정한다.** 사용자가 지적한 실제 예(전→후)를 모아 지시서에 **원문 그대로** 넣는다. 그냥 "어색한 곳을 찾아라"만 쓰면 일반적인 AI 문장으로 "개선"된다. 같은 부류(섹션명·번역투·어휘·비유)를 찾게 한다.
2. **리뷰는 읽기 전용이라 장끼리 병렬로 돌려도 된다.** 리뷰어는 파일을 쓰지 못할 수 있으니 보고서 전문을 오케스트레이터가 scratchpad 의 `review-chNN.md` 로 저장하고, 수정 지시서에는 그 경로를 준다(BLOCK 은 요약하지 않고 원문으로).
3. **수정(쓰기)은 순차로.** 모든 장이 `book.js` 의 `BOOK`·`TERMS` 를 공유하므로 쓰는 에이전트는 한 번에 하나만 돌린다. 이전 장의 재검수(읽기 전용)와 다음 장의 수정은 동시에 돌려도 된다.
4. 페이지 수가 바뀌는 제안(분할 등)은 커리큘럼 변경이므로 사용자에게 먼저 묻는다. 접는 상자(`details.fold`)로 정리하는 안이 페이지 번호와 인용을 건드리지 않아 우선이다.
5. 어휘·제목을 바꾸면 연쇄 수정(장 제목 → `book.js`·README·`authoring/`·다른 장 링크·다른 장의 인용 문구)을 한 번에 정리한다. 한 장의 재검수 PASS 뒤 커밋(장마다 하나).
6. 수정 에이전트의 일괄 치환 사고(`\t` → 탭)를 막기 위해 매 장 커밋 전에 오케스트레이터가 제어문자 grep 을 직접 한 번 돌린다.

## 금기

- 장 본문을 직접 고치지 않는다. 오탈자도 수정 모드로 시킨다(장부·리뷰 이력 일치).
- 리뷰 PASS 없이 커밋하지 않는다. 집필자의 "통과했다"로 리뷰를 생략하지 않는다.
- 리뷰 지적을 요약하지 않고 원문으로 전달한다.
