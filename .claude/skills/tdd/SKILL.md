# TDD 오케스트레이터

메인 에이전트는 **오케스트레이터**다. 직접 코드를 짜지 않고, 워크스페이스를 준비하고, 각 단계를 전용 서브에이전트에 위임하고, 결과를 검증하고, git 히스토리를 관리한다. 계획과 RED/GREEN/REFACTOR 각 단계는 **별도 서브에이전트**에서 실행되어 각자 깨끗한 컨텍스트로 시작한다.

각 단계는 매칭되는 `subagent_type`으로 띄운다. 세부 작업 규칙은 각 서브에이전트 정의에 들어 있으니, 오케스트레이터는 아래 흐름과 규칙만 지키면 된다.

| 단계 | subagent_type |
|------|---------------|
| PLAN | `tdd-planner` |
| RED | `tdd-red` |
| GREEN | `tdd-green` |
| REFACTOR | `tdd-refactor` (`/simplify` 사용) |
| 문서 | `tdd-docs` |

서브에이전트는 컨텍스트를 공유하지 않으므로, **호출할 때마다 feature-slug, 사이클 번호/설명, 테스트 프레임워크, 관련 파일 경로를 명시적으로 넘긴다.**

## 모델 선택

각 단계는 서브에이전트의 기본 모델로 호출하되, 오케스트레이터가 사이클 복잡도에 따라 호출 시 `model` 파라미터를 조정한다.
- **red·green·refactor**: 기본 `sonnet`. 설계 판단이 큰 복잡한 사이클은 `opus`로 올려 호출한다. 코드 품질이 핵심이므로 haiku로는 내리지 않는다.
- **docs**: 기본 `sonnet`. 변경이 사소하면 `haiku`로 내려 호출할 수 있다.
- **planner**: 한 기능당 한 번 도는 고레버리지 단계이므로 세션 모델(`inherit`)을 유지한다.

## 흐름

**Stage 0 — 준비 (오케스트레이터)**
1. git 저장소이고 작업 트리가 깨끗한지 확인. 변경사항이 남아 있으면 멈추고 사용자에게 물어본다 (단계별 커밋 규율이 깨끗한 시작에 의존).
2. 요청에서 짧은 feature-slug를 정한다 (예: `user-auth`).
3. 새 브랜치 `tdd/<feature-slug>` 생성 후 체크아웃.
4. plan 파일 경로: `.tdd/<feature-slug>-plan.md`.

**Stage 1 — PLAN (`tdd-planner`)**
`tdd-planner`를 띄워 기능을 N개의 사이클로 분해하고 plan 파일을 작성하게 한다. 보고된 계획을 **검토**(사이클 크기·순서·완전성)하고 필요하면 조정한 뒤, plan 파일을 **단독 커밋**:
```
git add .tdd/<feature-slug>-plan.md
git commit -m "docs(tdd): <feature-slug> 계획 수립 (<N>개 사이클)"
```
계획이 타당할 때만 다음으로 진행한다.

**Stage 2 — 사이클 반복**
각 사이클을 순서대로 RED → GREEN → REFACTOR로 진행한다. 각 단계는 해당 서브에이전트가 작업하고 **자기 단계 파일만 커밋**한다. 오케스트레이터는 단계 사이마다 실제 테스트 출력으로 red/green 상태를 **검증**한 뒤 다음으로 넘어간다.
- **RED** (`tdd-red`): 이번 사이클 동작에 대한 실패하는 테스트 작성 후 커밋. 통과해버리면 새 동작을 테스트하지 않는 것 → 되돌려보낸다.
- **GREEN** (`tdd-green`): 테스트를 통과시키는 최소 코드 작성 후 커밋.
- **REFACTOR** (`tdd-refactor`): `/simplify`로 이번 사이클 코드를 정리하고 테스트 green 유지. 변경이 있으면 `refactor` 커밋, 없으면 GREEN 커밋에 amend하여 "검토했으나 변경 없음"을 기록한다 (skip 여부를 히스토리에서 확인하기 위함).

사이클이 끝나면 오케스트레이터가 plan 파일의 해당 항목을 체크(`- [ ]` → `- [x]`)하고 plan 파일을 **단독 커밋**:
```
git add .tdd/<feature-slug>-plan.md
git commit -m "docs(tdd): 사이클 N 완료 — <사이클 제목>"
```

**Stage 3 — 문서 (`tdd-docs`, 모든 사이클 종료 후)**
모든 사이클이 끝나면 `tdd-docs`를 한 번 띄운다. plan 파일과 git log로 작업을 복원해 영향받는 문서·백로그·버그리포트를 갱신하고 별도 커밋한다.

**Stage 4 — 마무리 (오케스트레이터)**
사용자에게 보고: 브랜치명, 사이클 수, 각 사이클 한 줄 요약, skip된 REFACTOR(와 이유), 문서 변경 내역. 브랜치는 체크아웃된 채로 두고, 요청 없이는 merge/push하지 않는다.

## 규칙

- **실패하는 테스트 없이 구현 코드를 쓰지 않는다.** "그냥 코드부터" 하고 싶어지면 그게 RED 테스트를 먼저 쓰라는 신호다.
- **한 사이클 = 한 동작.** 한 사이클 테스트에 서로 무관한 assertion이 여럿 필요하면 사이클이 너무 큰 것 → 쪼갠다.
- **plan 파일은 항상 단독 커밋.** 코드 단계는 plan을 포함하지 않고, plan 단계는 코드를 포함하지 않는다.
- **신뢰하지 말고 검증한다.** 단계 사이마다 실제 테스트 출력으로 red/green을 확인한다.
- **서브에이전트는 자기 단계 파일만 커밋한다.** `git add -A` 금지, 정확한 경로를 넘긴다.
